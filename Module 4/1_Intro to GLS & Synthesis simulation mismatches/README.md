# Gate Level Simulation and Synthesis-Simulation Mismatch

## Gate Level Simulation (GLS)

### What is GLS?

Gate Level Simulation (GLS) is the process of simulating a **synthesized gate-level netlist** using a testbench.

Instead of simulating the original RTL design, the synthesized netlist becomes the **Design Under Test (DUT)**.

The gate-level netlist represents the hardware generated by the synthesis tool using standard cells from the target technology library.

---

## Why GLS?

GLS is performed after synthesis to:

- Verify the **logical correctness** of the synthesized design.
- Check that synthesis has not changed the intended functionality.
- Verify the behaviour of the actual gate-level implementation.
- Identify issues that may not be visible during RTL simulation.
- Validate timing when delay information is available.

The main objective is to make sure that:

```text
RTL Behaviour = Synthesized Netlist Behaviour
```

---

## Types of GLS

GLS can be broadly divided into two types.

### Timing-Aware GLS

Timing-aware GLS uses delay-annotated gate-level models to verify both:

It can be used to check:

- Cell propagation delays
- Setup and hold behaviour
- Timing violations

Timing-aware GLS was introduced in the theory but was not covered in detail.

---

### Functional GLS

Functional GLS checks whether the synthesized netlist behaves logically the same as the original RTL design.

The main focus is **functional correctness**.

## GLS Using Icarus Verilog

GLS uses three main components:

- Design RTL / synthesized netlist
- Gate-level Verilog models
- Testbench

The gate-level Verilog models are simulated using Icarus Verilog and the resulting waveform is viewed using GTKWave.

The simulation produces a `.vcd` file containing the signal transitions, which can then be analysed using GTKWave.

# Synthesis-Simulation Mismatch

A synthesis-simulation mismatch occurs when the behaviour observed during **RTL simulation differs from the behaviour of the synthesized design**.

Ideally:

```text
RTL Simulation
      =
Gate-Level Simulation
```

A mismatch usually indicates a problem with the RTL coding style or a construct that is interpreted differently by simulation and synthesis.

The main causes discussed were:

- Missing sensitivity list
- Incorrect blocking and non-blocking assignments
- Non-standard Verilog coding

---

# Missing Sensitivity List

Consider a multiplexer written as:

```verilog
always @(sel)
begin
    if (sel)
        y = i1;
    else
        y = i0;
end
```

The sensitivity list contains only `sel`.

Therefore, the simulator reevaluates the `always` block only when `sel` changes.

If `i0` or `i1` changes while `sel` remains unchanged, the block is not triggered again.

This can produce incorrect simulation behaviour for the intended combinational logic.

### Correct Coding

```verilog
always @(*)
begin
    if (sel)
        y = i1;
    else
        y = i0;
end
```

`always @(*)` automatically includes all signals used inside the block in the sensitivity list.

### Main Idea

```text
Missing input in sensitivity list
            ↓
Simulation does not reevaluate
            ↓
Incorrect simulation behaviour
            ↓
Possible synthesis-simulation mismatch
```

# Blocking vs Non-Blocking Statements

Verilog provides two main procedural assignment operators:

```text
=   → Blocking assignment
<=  → Non-blocking assignment
```

## Blocking Assignment

Blocking assignments execute in the exact order in which they are written.

Example:

```verilog
always @(*)
begin
    a = b;
    c = a;
end
```

The first statement executes before the second statement.

Therefore:

```text
b → a
a → c
```

Blocking assignments are generally used for **combinational logic**.

---

## Non-Blocking Assignment

Non-blocking assignments evaluate the right-hand sides and schedule the left-hand-side updates.

Example:

```verilog
always @(posedge clk)
begin
    q1 <= d;
    q2 <= q1;
end
```

Both RHS expressions are evaluated using the values present before the register updates.

This models the behaviour of multiple flip-flops updating at the same clock edge.

Therefore, non-blocking assignments are generally used for **sequential logic**.

```text
Clock Edge
    ↓
Evaluate RHS
    ↓
Update registers
```

---

# Blocking Assignment Caveat

Consider:

```verilog
always @(*)
begin
    y  = q0 & c;
    q0 = a | b;
end
```

Here, `y` is calculated before `q0` is updated.

Therefore, during simulation, `y` uses the **previous value of `q0`**.

However, the intended combinational hardware may represent:

```text
q0 = a | b
y  = q0 & c
```

which gives:

```text
y = (a | b) & c
```

This difference between procedural simulation order and the intended combinational hardware can create unexpected simulation behaviour.

# Main Causes of Synthesis-Simulation Mismatch

| Cause | Effect |
|---|---|
| Missing sensitivity list | Simulation may not update when an input changes |
| Incorrect blocking usage | Simulation can depend on statement order |
| Incorrect non-blocking usage | Can introduce unexpected delta-cycle behaviour |
| Non-standard Verilog coding | Synthesis and simulation may interpret the design differently |

---

# Key Takeaway

Gate Level Simulation is used to verify the **logical correctness of the synthesized design**.

Functional GLS checks whether the synthesized netlist behaves like the RTL, while timing-aware GLS additionally considers cell and interconnect delays.

Synthesis-simulation mismatches can occur because a simulator executes Verilog statements according to simulation semantics, while synthesis interprets the same code as hardware.

Therefore, proper Verilog coding practices are essential:

```text
Combinational logic  → always @(*) + blocking assignment (=)

Sequential logic    → clocked always block + non-blocking assignment (<=)
```
